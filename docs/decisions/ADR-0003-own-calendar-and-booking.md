# ADR-0003: собственный календарь и запись

## Контекст

Календарь — источник истины для бота и кабинета. Психолог задаёт рабочие дни и часы, клиент записывается на любое свободное время в их пределах. Две одновременные записи на одно время недопустимы. Клиенты могут жить в других часовых поясах.

## Решение

### Данные

```
practice_settings   zone (ZoneId), lead_time, horizon, slot_step
work_schedule       weekday, start_time, end_time               -- недельный шаблон, время местное в zone
schedule_override   date, closed | [start_time, end_time]       -- отпуск, праздник, особый день
session_type        code, title, duration, buffer, price, first_visit, active
session             id, client_id, type_id, starts_at, ends_at, occupied tstzrange,
                    status, price_snapshot, policy_version, rescheduled_to, created_by
```

- Время сессии хранится мгновением (`timestamptz`). Шаблон расписания хранится местным временем с поясом психолога: «вторник 10:00–18:00» не должен съезжать при смене смещения пояса.
- `occupied = [starts_at, ends_at + buffer)` — занятый интервал с перерывом после сессии.
- `price_snapshot` и `policy_version` фиксируются при записи. Изменение цены или политики не меняет условий уже назначенной сессии ([ADR-0004](ADR-0004-cancellation-policy-and-charges.md)).
- Сущности «специалист» нет: психолог один. Второй специалист — миграция данных, а не заранее заложенная общность.

### Целостность

```sql
CREATE EXTENSION IF NOT EXISTS btree_gist;
ALTER TABLE session ADD CONSTRAINT session_no_overlap
  EXCLUDE USING gist (occupied WITH &&) WHERE (status IN ('BOOKED', 'REQUESTED'));
```

Пересечение отвергает база, а не проверка в коде перед вставкой. Из двух одновременных записей на один слот вторая получает отказ условной записи (`ConditionalWriteResult` из `platform-persistence`). Бот отвечает «время только что заняли» и предлагает соседние слоты.

### Свободные слоты

Операция чтения без побочных эффектов (`REQ-CODE-DESIGN-003` ядра):

1. Диапазон дат ограничен `[now + lead_time, now + horizon]`.
2. Для каждой даты: интервалы шаблона дня недели, заменённые исключением этой даты, если оно есть.
3. Интервалы переводятся в мгновения через пояс психолога.
4. Внутри интервала слоты ставятся с шагом `slot_step`. Слот годится, если `[start, start + duration + buffer)` помещается в интервал и не пересекает `occupied` занятых сессий.

Слоты не хранятся. Изменение расписания сразу меняет выдачу, и записи «висящих» слотов не нужно пересчитывать.

### Состояния сессии

| Из | Команда | В |
|---|---|---|
| `REQUESTED` | `confirm` | `BOOKED` |
| `REQUESTED` | `decline` | `DECLINED` |
| `BOOKED` | `complete` | `COMPLETED` |
| `BOOKED` | `markNoShow` | `NO_SHOW` |
| `BOOKED` | `cancel` | `CANCELLED` |
| `BOOKED` | `reschedule` | `CANCELLED` со ссылкой `rescheduled_to` на новую `BOOKED` |

- `REQUESTED` — только если первичная консультация требует подтверждения психолога (вопрос 1).
- Перенос — одна транзакция: новая сессия создаётся, старая отменяется со ссылкой `rescheduled_to`. Если новый слот занят, старая сессия не трогается.
- Каждый переход — командная операция с явным именем и тестом (`REQ-CODE-DESIGN-004` ядра).
- Закрытие прошедших сессий (`BOOKED → COMPLETED`) — периодическая команда. Неявку отмечает психолог.

### Кто что может

| Действие | Клиент | Психолог |
|---|---|---|
| Запись | Только в свободный слот | В любое время, в том числе вне расписания, с предупреждением |
| Перенос, отмена | Своих сессий, через решение политики | Любых. Штраф — по выбору: по политике или без штрафа |
| Неявка | — | Отмечает |

### Часовые пояса

Пояс психолога — в `practice_settings`. Пояс клиента Mini App берёт из браузера (`Intl.DateTimeFormat().resolvedOptions().timeZone`) и сохраняет в карточке. Бот показывает время в поясе клиента с подписью пояса, если он отличается от пояса психолога.

## Отклонённые варианты

- **Хранить слоты таблицей.** Нужна пересборка при каждом изменении расписания, а расхождение таблицы и шаблона становится отдельным видом дефекта.
- **Проверка пересечения в коде.** Без блокировки таблицы проверка и вставка не атомарны, и двойная запись становится вопросом времени.
