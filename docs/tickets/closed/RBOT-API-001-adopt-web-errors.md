# Ошибки API отдаются одним контрактом ProblemDetail

## Проблема

Сервис отдаёт ошибки собственной формой тела и раскладывает отображение исключений в статусы по локальным обработчикам. Клиент разбирает столько контрактов, сколько сервисов, а код ошибки держится на совпадении литералов и ничем не проверяется.

## Основание

Обязательство ядра `web-errors`, требование `REQ-API-001`, объявлено в версии ядра 1.5.0. Срок исполнения: 2 выпуск(ов) потребителя.

## Последствия при сохранении текущего поведения

Требование ядра действует, а проект ему не соответствует: расхождение обнаруживается не проверкой, а при следующем изменении в этой области.

## Требуется

1. Контракт ошибок соблюдён: локальные обработчики общих исключений и собственные типы тела ошибки удалены. Штатный путь — starter `platform-web-errors`; собственная реализация, удовлетворяющая контракту, ему равноценна (`REQ-ADOPTION-021`).
2. Соответствие исключений кодам и статусам объявлено портом `ErrorCodeResolver` проекта.
3. Тексты `detail` даёт порт `ErrorMessages`, если проекту нужны собственные сообщения; реализация по умолчанию сообщений исключений не раскрывает.
4. Клиент разбирает `ProblemDetail` с расширением `code`; поддержки прежнего формата не остаётся.
5. Клиент подключает `@apocarteres/http`: требуется Angular 22 и rxjs 7.8 — библиотека объявляет их одноимёнными зависимостями `peerDependencies`.
6. Перехватчики регистрируются как функциональные: `provideHttpClient(withInterceptors([sanitisingInterceptor, sessionExpiredInterceptor]))`. Схема с `HttpClientModule` и `HTTP_INTERCEPTORS` для них не годится.
7. Обработчик истёкшей сессии объявлен провайдером токена `SESSION_EXPIRED` и принимает запрос и разобранный отказ: без него первый ответ 401 роняет запрос названной ошибкой.
8. Сервису, которому нужны собственные поля в теле ошибки или заголовки ответа, объявлены порты `ErrorExtensions` и `ErrorHeaders`; локальных обработчиков для этого не остаётся. Клиент читает эти поля через `ApiFailure.extensions`, своего разбора тела не заводит.

## Критерии приёмки

- Ошибки всех статусов отдаются как `application/problem+json` с полями RFC 9457 и расширением `code`.
- В проекте не осталось локального обработчика, отображающего общее исключение в статус.
- Перечень кодов ошибок проекта сверен тестом со словарём клиента.
- Обработка ошибок в клиенте переведена с `HttpErrorResponse` на `ApiFailure`: местами, где проверялся тип ответа HTTP, проверяется разобранный отказ.

## Ход работы

- 2026-09-30: служба отдаёт ошибки стартером `platform-web-errors` с первого дня (MVP-01): своих обработчиков исключений и типов тела ошибки нет. Коды проекта — `AccountRefused` (`roles-rejected`, `account-missing`, `self-change-refused`), остальное — коды ядра. Сообщений исключений `detail` не раскрывает: `ErrorMessages` по умолчанию.
- Клиент: `sanitisingInterceptor` и `sessionExpiredInterceptor` из `@apocarteres/http` в `withInterceptors`; `SESSION_EXPIRED` — `frontend/shared/session-expired.ts` (на `authentication-required` ведёт на вход); разбор отказа — `ApiFailure` в `frontend/shared/failures.ts` вместо разбора `HttpErrorResponse`.
- `ErrorCodesMatchClientTest`: каждый код `AccountRefused` и показываемые коды ядра есть в словаре клиента.
- `AdminAccountsIT.failuresOfEveryStatusAreProblemDetails`: 401, 400, 404 отдаются как `application/problem+json` с полем `code`, 404 учётной записи — `account-missing`.
- Собственных полей тела и заголовков ошибок у проекта нет, порты `ErrorExtensions` и `ErrorHeaders` не нужны.
