# Своя аутентификация проекта заменена аутентификацией ядра

## Проблема

Проект ведёт свою аутентификацию: учётные записи, сессии, токены действий, ограничение частоты. Такую же аутентификацию пишет каждый проект, и расходится она там, где расходиться не должно: правило пароля, сроки сессии и токенов, хранение почты в индексе сессий.

## Основание

Обязательство ядра `core-auth`, требование `REQ-AUTH-001`, объявлено в версии ядра 6.1.0. Срок исполнения: 3 выпуск(ов) потребителя.

## Последствия при сохранении текущего поведения

Требование ядра действует, а проект ему не соответствует: расхождение обнаруживается не проверкой, а при следующем изменении в этой области.

## Требуется

1. Учётные записи перенесены в таблицы ядра (sql/platform-auth/create-*.sql) переходом базы; хеши BCrypt переносятся как есть, доменный профиль ссылается на учётную запись (REQ-AUTH-001, REQ-AUTH-007).
2. Объявлены роли проекта и роли новой учётной записи: platform.auth.roles, platform.auth.default-roles (REQ-AUTH-002).
3. Объявлены порты AuthLetters, HumanCheck, RegistrationHook, ApiAccess, EntryAccess — каждый своей реализацией или явной заглушкой (REQ-AUTH-003, REQ-AUTH-010, REQ-AUTH-014, REQ-AUTH-016).
4. Собственные контроллер входа, сессии, токены действий и ограничитель частоты сняты; прочие ограничения проекта идут через platform-rate-limit (REQ-AUTH-011).
5. Клиент объявляет provideAuth() и authInterceptor; формы проекта работают через AuthSession (REQ-AUTH-015).
6. Экраны администратора работают через Accounts: создание, назначение пароля, поиск; своих записей в таблицы ядра нет (REQ-AUTH-001, REQ-AUTH-009).
7. Профиль регистрации — класс проекта, объявленный в RegistrationHook<P>; поля проверяются аннотациями Bean Validation (REQ-AUTH-021).

## Критерии приёмки

- Вход, регистрация с подтверждением и сброс пароля проходят на стенде через точки /api/auth/*.
- Пользователь, зарегистрированный до перехода, входит прежним паролем.
- Индекс сессий в Redis не содержит почты.
