# Клиент из Telegram не проходит через цепочку безопасности ядра

## Проблема

Клиенты сервиса приходят из Telegram: обновления бота через webhook и запросы Mini App. Их подлинность подтверждается секретным заголовком `X-Telegram-Bot-Api-Secret-Token` и подписью `initData`, а не сессией учётной записи ядра. Цепочка безопасности ядра на `/api/**` принимает только сессию и ключи доступа учётной записи. Порта для такого клиента в ней нет.

## Подтверждение

Ядро `v13.4.0`, чтение кода (`f255450`):

- `platform-auth/.../internal/AuthAutoConfiguration.java:170` — единственная цепочка `platformApiSecurity`, `securityMatcher("/api/**")` в строке 179.
- `REQ-AUTH-022`: модуль объявляет правила доступа бином `ModuleApiAccess`, а не своей цепочкой. `ModuleApiAccess` задаёт только правила авторизации, аутентифицировать запрос он не может.
- Единственный встроенный способ аутентификации кроме сессии — `AccessKeyFilter` (строки 177, 194): фильтр перед `CsrfFilter` и исключение из CSRF для запросов по ключу. Он привязан к ключу учётной записи ядра (`REQ-AUTH-028`–`REQ-AUTH-030`).
- Учётная запись ядра требует настоящую почту (`REQ-AUTH-001`, `REQ-AUTH-003`), поэтому заводить учётную запись на каждого клиента Telegram нельзя (ADR-0002, вариант В).

Проверено чтением кода, а не отказом теста: кода проекта ещё нет.

## Последствия при сохранении текущего поведения

Проект заводит вторую цепочку `SecurityFilterChain` вне `/api/**` для `/tg/webhook` и `/miniapp/api/**` (ADR-0002, вариант А). Ответы об отказе, ограничение частоты, метрики отказов и порядок цепочек поддерживаются вручную рядом с ядром. Виджет на сайте (вход через Telegram Login или по одноразовому коду) добавит третий способ в ту же самодельную цепочку.

## Ожидаемый результат

В ядре есть порт внешней личности. Ядро по образцу `AccessKeyFilter`:

1. на объявленных проектом путях вызывает порт проекта, который по запросу возвращает личность проекта с ролями или отказ;
2. исключает эти пути из CSRF, потому что подлинность несёт подпись запроса, а не cookie;
3. отвечает об отказе, ограничивает частоту и считает метрики так же, как для сессии и ключа;
4. даёт коду проекта узнать личность запроса, как `CurrentAccount` для учётной записи.

## Критерии приёмки

- Ядро ответило на заявку задачей или отказом с причиной (`REQ-ADOPTION-020`).
- Если порт выпущен: модули `telegram` и `miniapp` переведены на него в одном изменении, собственной цепочки в проекте нет, тесты MVP-04 и MVP-08 на отказ при неверной подписи проходят.
- Если отказ: причина записана в ADR-0002, вариант А зафиксирован как окончательный, задача закрыта.
