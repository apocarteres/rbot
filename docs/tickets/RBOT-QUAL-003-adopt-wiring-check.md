# Проверка проводки входит в набор check

## Проблема

Набор `check` не поднимает приложение, поэтому отказы уровня запуска — отсутствующий бин, условная конфигурация, не сработавшая в этом рантайме, несошедшиеся границы транзакций — не мешают отправке изменений. Зелёный `check` читается как «можно отправлять», хотя приложение может не запуститься.

## Основание

Обязательство ядра `wiring-check`, требование `REQ-QUALITY-012`, объявлено в версии ядра 1.3.0. Срок исполнения: 2 выпуск(ов) потребителя.

## Последствия при сохранении текущего поведения

Требование ядра действует, а проект ему не соответствует: расхождение обнаруживается не проверкой, а при следующем изменении в этой области.

## Требуется

1. Для каждого рантайма компонента есть тест, поднимающий контекст приложения без внешних служб: без базы, брокера, сети и учётных данных.
2. Тесты проводки входят в набор `check`, а не в `verify`.
3. Рантаймы перечислены явно: веб-приложение, консольные команды, обработчики очередей — каждый способ запуска проверяется отдельно.

## Критерии приёмки

- `check` роняется, если бин, нужный одному из рантаймов, отсутствует в его контексте.
- Проверка проводки не требует внешних служб и укладывается в секунды.
- Набор `check` остаётся быстрым: минуты, а не десятки минут.

## Ход работы

- 2026-09-30: рантаймы — веб-служба и запуск `migrate`. `ApplicationWiringTest` поднимает контекст веб-службы без базы и Redis: источник данных, контейнер событий Spring Session и настройка уведомлений Redis подменены. `MigrateWiringTest` поднимает контекст `MigrationRun` без веба и проверяет, что прикладных бинов веб-службы в нём нет, а бин переходов есть.
- Оба теста — в `backend-test`, набор `check`; вместе около 3 с.
- Заведомый отказ: снятый `@Service` у `AccountAdministration` роняет `ApplicationWiringTest` с `NoSuchBeanDefinitionException`; правка возвращена.
