# Неизвестный адрес отвечает как неизвестный: порт клиента и 404 на сервере

## Проблема

Обычная раскладка одностраничного клиента отдаёт точку входа приложения на любой путь, поэтому любой адрес отвечает 200 и страницей. Человек с опечаткой в ссылке молча попадает на рабочую страницу, а разбор того, что отдаётся наружу, по кодам ответа невозможен: поиск утечки читает 200 и на существующем, и на несуществующем.

## Основание

Обязательство ядра `unknown-path`, требование `REQ-DEPLOYMENT-018`, объявлено в версии ядра 1.42.0. Срок исполнения: 3 выпуск(ов) потребителя.

## Последствия при сохранении текущего поведения

Требование ядра действует, а проект ему не соответствует: расхождение обнаруживается не проверкой, а при следующем изменении в этой области.

## Требуется

1. Маршруты клиента собираются портом withUnknownPath из пакета @apocarteres/routing: страница «не найдено» объявлена и отличается от рабочих страниц проекта (REQ-DEPLOYMENT-018).
2. Свой маршрут неизвестного пути снят: на него отвечает порт ядра.
3. Адрес с расширением при отсутствии файла отвечает 404; маршруты приложения расширений не имеют, поэтому глубокие ссылки не страдают.
4. Префиксы API объявлены с признаком точного совпадения (^~): совпавшее регулярное выражение побеждает обычный префикс и иначе перехватит обращения к API.
5. После развёртывания выполняется conventions unknown --url <адрес сайта>.

## Критерии приёмки

- Маршруты собираются `withUnknownPath`; попытка объявить рабочую страницу страницей «не найдено» роняет запуск приложения.
- Неизвестный адрес без расширения показывает страницу «не найдено», а не рабочую страницу.
- `conventions unknown` проходит на рабочей среде; до правки раскладки он обязан отказывать — проверено заведомым отказом один раз при принятии.
- Обращение к API с точкой в адресе правилом по расширению не перехватывается.
