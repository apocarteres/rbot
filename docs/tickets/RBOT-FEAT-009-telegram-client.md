# Клиент через Telegram: приглашение, согласие, Mini App

## Проблема

Клиент входит только по почте и паролю, которые заводит администратор. Владелец хочет проверить сервис на рабочей среде под одним аккаунтом Telegram как клиент и под учётной записью кабинета как психолог.

## Подтверждение

Решения владельца от 2026-10-01, макет согласован в тот же день:

- клиентом становятся только по приглашению из кабинета; посторонний получает просьбу попросить ссылку;
- согласие на обработку данных — черновым текстом кнопкой, с записью версии, до ответа юриста (ADR-0005, вопрос 4);
- рабочий хост не достаёт до `api.telegram.org` (проверено 2026-10-01, IPv4 и IPv6); исходящие запросы к Bot API идут через прокси на `metrics`;
- бот — `@psy_receptionist_bot`, токен положен владельцем в `/etc/rbot/rbot.env` под именем `TELEGRAM_BOT_TOKEN`; подготовка прокси переименовывает ключ в `RBOT_TELEGRAM_BOT_TOKEN`.

## Последствия при сохранении текущего поведения

Сценарий клиента на рабочей среде не проверить: клиентских учётных записей там нет, а заводить их вручную на каждого клиента — не путь MVP.

## Требуется

1. Кабинет, раздел «Клиенты»: «Пригласить клиента» с подписью, которую видит только психолог; ссылка `t.me/<бот>?start=<токен>` на 30 дней, одноразовая, в базе — только хеш токена; «Новая ссылка» гасит прежнюю.
2. Бот (`/api/tg/webhook` за портом ядра, секрет webhook): `/start <токен>` → черновое согласие → кнопка «Согласен» → привязка Telegram к карточке, запись согласия с версией; без приглашения — просьба попросить ссылку; привязанному — кнопка приложения. Повтор `update_id` не обрабатывается.
3. Mini App: `/api/miniapp/**` за портом ядра, подпись `initData` и срок `auth_date` 1 час; те же запись, перенос и отмена, что у клиента по почте. Непривязанный Telegram — `client-not-linked`.
4. Уведомления клиенту, когда психолог записывает, переносит или отменяет его сессию.
5. Прокси: `tinyproxy` на `metrics` слушает только `127.0.0.1` и пропускает только `api.telegram.org:443`; рабочий хост ходит к нему SSH-туннелем с ключом, которому разрешён только этот проброс. Регистрация webhook и кнопки меню — при раскате.

## Критерии приёмки

- `InitDataTest`: подпись токеном даёт пользователя; чужой токен, правка поля, устаревшая дата отвергаются.
- `TelegramIT`: webhook без секрета — 401; приглашение → `/start` → согласие → привязка; повторное согласие по той же ссылке — отказ; Mini App с подписью — запись, с чужой подписью — 401, непривязанный — 403; отмена психологом уведомляет клиента; токен приглашения в базе не хранится.
- Рабочая среда: владелец получает ссылку в кабинете, привязывает Telegram, записывается в Mini App; психолог видит запись в «Записях».

## Ход работы

- 2026-10-01: переходы `rbot:007-client-invites` (подпись, `telegram_user_id`, приглашения, согласия) и `rbot:008-telegram-updates`. Модуль `telegram`: `InitData`, `TelegramAuthentication` (два `RequestAuthenticator`), `UpdateHandler`, `RestBotGateway` через прокси, `SessionNotices` после фиксации транзакции, тексты бота — `telegram/messages.properties`. Запись переведена на идентификатор карточки клиента: одни команды для входа по почте и для Telegram. Роли внешней личности — `TELEGRAM_CLIENT`, `TELEGRAM_SERVER`.
- Кабинет: раздел «Клиенты», окно `InviteDialog`; выбор клиента в окне записи — по подписи. Приложение клиента: режим Telegram по `tgWebAppData` из адреса, без библиотеки Telegram.
- Инфраструктура: `scripts/deploy/provision-telegram-proxy.sh`, `deploy/systemd/rbot-telegram-tunnel.service`, `scripts/ops/telegram-setup.sh` в раскате.
- 152-ФЗ: сообщения бота проходят через сервер в Финляндии и Telegram; черновик согласия это называет. Текст согласия — до ответа юриста.
